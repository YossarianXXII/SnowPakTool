# SnowPakTool Desktop

A small Windows Forms interface over the original SnowPakTool source classes. The workflow keeps the source PAK intact, extracts both the outer PAK and its `initial.cache_block`, opens the workspace for manual edits, and creates a new PAK at a selected output path.

All desktop tabs use one shared text search: double-tap **Shift**, then enter at least **3 characters**. Matching text is highlighted in the current tab and its selected sub-tab, including control labels/values, table headers/cells, tooltips and attached detail data. Inactive tabs are excluded. Search never filters rows or changes checkbox/dropdown values. **Enter** brings the first match into view and focuses it. **Esc**, an outside click, changing tabs or switching windows dismisses the popup and clears highlights. Results refresh when current-tab data changes.

## Run

### Double-click the published app

Double-click `Start SnowPakTool GUI.lnk` in this folder, or open `publish_exponential_slider` and double-click `SnowPakTool.Desktop.exe`. Keep the files in `publish_exponential_slider` together; the GUI executable loads the adjacent assemblies and requires the .NET 10 Windows Desktop Runtime. `SnowPakTool.exe` in that folder is the separate command-line tool.

### Run from source

From the repository root:

```powershell
dotnet run --project .\SnowRunnerTools-master\src\SnowPakTool.Desktop\SnowPakTool.Desktop.csproj
```

Choose `initial.pak`, select a workspace folder, and click **Unpack / merge PAK + cache block**. The app remembers the last selected PAK and workspace paths between launches. Existing workspace files are compared with the files being unpacked: identical files are skipped. Before applying any replacements, the app lists every differing file in one table. Choose the incoming PAK version or keep the workspace version for each row, select **Take all changes in new file** to use every PAK version, or open **View changes** to edit a file before applying it. Canceling review leaves existing workspace files unchanged. Binary conflicts can be selected, but cannot be edited in the text pane. After unpacking, click **Pack to new PAK…** and choose an output filename. If that file already exists, the save dialog asks before replacing it; the completed archive is written to a temporary file before replacing the selected output.

The **Experience / Ranks** tab reads `[ps]/rank_settings.sso` from the selected workspace. Use the fixed **Stage changes** toolbar to snapshot the current XP preview; the values survive restarts and appear as pending on Start. Only **Start → Apply pending changes** writes that snapshot. Later preview edits are excluded until staged again. **Revert unstaged edits** restores the snapshot or file values, and **Revert staged changes** clears the snapshot and restores file values in the preview. Amber/green XP highlights and hover details distinguish preview, staged and applied values. Its calculated progression uses an exponential curve, with controls for curve steepness and a slider that reduces the selected-region XP budget in 5,000 XP steps. The displayed exponential formula updates with each steepness adjustment. Generated XP values are rounded to the nearest 100 XP. The region checklist and graphs follow the saved Region progression order and refresh on return to the editor. Unlisted regions append in release order; change the route in Randomizer -> Region progression. Region selections, XP controls and staged values remain independent of that order. Each graph has a corner button to swap the region-order and level axes. The app restores the last window size when reopened.

The desktop project references the original `SnowPakTool` project and calls its `CacheBlockReader`, `CacheBlockWriter`, and `ZipPakHelper` classes. It targets .NET 10 Windows Forms.

The **Game data → Trucks-Cargo** sub-tab lists cargo types and carrier variants from the active workspace, including DLC and sparse workspace updates. Use the shared double-Shift search for cargo names, types, variants, content packs and properties; click column headers to sort. The table shows the defined cargo length, loose weight (per cargo unit), packed weight (sum of addon physics body masses), and cargo value. Log cargo length represents carrier slots; body mass can include carrier parts. Blank numeric values mean the value is not explicitly defined. Select a row for its localized description and attributes from the cargo type, packed addon, matching loose models and referenced loose body templates. Loose models are matched by cargo type and slot count; static scenery is excluded. For logs, loose weight is one individual log and packed weight is the complete load. Missing or unresolved weights and differing loose-model weights remain blank. Simple loose body mass templates are resolved; full file inheritance and complex body template hierarchies remain unresolved. To increase both weights, multiply every packed body mass and the matching loose model body masses by the same factor; prefer a local Mass override over changing a shared template. **Reload cargo** refreshes the workspace data after external edits and discards unstaged previews. The main table has one Loose and one Packed weight column. Double-click either cell, or press Enter/F2, to open its body-mass popup. Each popup row shows the exact indexed XML body path, model frame and source file; only the raw Mass value is editable. OK updates the preview and Cancel discards all popup edits. The popup also offers Reset to original values; staging and Apply remain separate. Values accept 0–1,000,000 kg, including decimals; blank removes the local Mass attribute. Template-based cargo receives a local body override, leaving shared templates unchanged. Cargo rows sharing a source body share the same preview. Changed popup values and main-table totals display new (original) values, amber for preview/staged and green for applied changes. Stage changes persists an explicit snapshot; only Start -> Apply pending changes writes the updated overlay. Revert unstaged edits restores the staged snapshot, Revert staged changes clears it, and Reset selected / Reset to original values previews preserved raw originals, including attribute absence. Global reset and staging include filtered rows. Apply checks every body identity and expected raw value before writing any cargo file and retains staged changes on conflict. Shared presets include cargo previews/staged edits.

The **Game data → Regions-Trucks** sub-tab reads truck placements from `[scene]/data_for_ssl.bin` inside installed `level_*.pak` files, or from extracted `level_*/[scene]/data_for_ssl.bin` folders. It detects common Steam install locations; **Map folder** can be changed manually. Select one or more region tiles in the top row to populate the table below. Selected tiles are highlighted. The **Obtainable** and **Mission** checkboxes independently control those truck groups; unverified rows always remain visible for review. Double-tap **Shift** to open the same search overlay as Tier List: at least three characters highlight matches and scrolls to the first; **Enter** selects a match. **Esc**, clicking elsewhere, switching windows, or leaving the page closes the overlay. Search covers all visible table values, hover details, evidence, source paths and region tile text; Tier List also searches tier/group names and descriptions. Search does not hide rows. Each placement remains a separate row, so collectible and mission-only copies of the same model are distinguishable.

Region tiles retain their 150 × 210 size and are sorted by original release order: the base-game regions followed by seasons 1–19. Each tile has a region-name header, a representative map screenshot from [MapRunner](https://www.maprunner.info/), and a season/counts footer. Thumbnails are embedded for offline use; the source manifest is in `Assets/Regions/sources.json`. Unrecognized future region IDs sort after known releases and retain a text fallback.

Tiles show only map/placement totals, plus an **unverified** count when it is greater than zero. Unverified rows have an editable **Availability** dropdown. Choose discovery/start, task reward, or mission/task-only; the choice saves immediately to `%LocalAppData%/SnowPakTool.Desktop/region-truck-availability.json`, scoped by map and placement ID. Saved choices survive reloads and restarts, update tile counts and filters, and remain editable if a correction is needed. Other known rows stay read-only. Availability review does not modify game data.

Confirmed placement exceptions take precedence over inferred task rules. The 17 placements confirmed by the user on 2026-11-01 are permanently classified **Mission/task only** in `RegionTruckPlacementOverrides.cs`. Exceptions use the map and placement ID, so other copies of the same truck model retain their own availability. They survive app restarts and workspace/map reloads; the evidence pane identifies the user-confirmed rule and confirmation date. Unrelated ambiguous placements still remain **Unverified**.

The truck table's **Tires** and **Addons** columns show each placement's map equipment, resolving blank configuration fields from the active workspace's vehicle defaults. Tires display **Highway**, **All-terrain**, **Offroad**, **Mudtires**, **Ice** (chains), or **Custom** (a tire definition compatible with only that truck in the current workspace). Hover over Tires for the specific tire name, wheel family, tire ID, rim and default/override information. Parent wheel definitions are followed when checking compatibility. If a map references a missing tire variant, the category is inferred from its stored ID where possible and the tooltip identifies the unresolved variant; unreadable equipment remains **Unknown**. Addons include explicitly installed equipment and default addons, with a map addon replacing the stock addon in the same socket. Hover over Addons for full names, IDs and default/map origins. These describe map placements rather than changes in a player save.

In this application, **visual addons** specifically means addon definitions stored in a folder whose name ends in `_tuning`. This user-defined grouping applies even to functional parts (such as diff locks or snorkels) placed in those folders. Each installed addon retains its source path, original game `Category`, map/default origin, and `IsVisual` flag in the catalog; the addon tooltip shows the grouping and category. Future requests to hide visual addons should use this folder-based flag rather than guessing from part names or gameplay effects.

The table excludes visual (`_tuning`) parts from both addon columns. The remaining equipment with `Category="frame_addons"` appears in **Frame addons**; the other remaining parts appear in **Addons**. Each column has a tooltip containing only that group's installed parts, including source IDs and default/map origins. The full installed-equipment metadata is retained for search and future filters. Empty groups display **None**.

The bottom details pane is resizable using the horizontal divider above it. It lists internal equipment by slot and name, visual addons by name with their game category in parentheses, vehicle properties and tire/wheel details. AWD/transfer-box and differential-lock components appear only under internal equipment, even when stored in a `_tuning` folder; the folder distinction remains in the underlying metadata. Placement, availability evidence, truck/map headings and frame/other addon lists are omitted from this pane. Vehicle property labels omit the TruckData/GameData prefixes and use spaces around =. Map overrides take precedence over vehicle socket defaults. Component names resolve through workspace definitions, including parent variant files; unresolved names fall back to their IDs. Definition properties are separate from player save-state values, and template-inherited settings are not presented as fully resolved. All displayed details participate in the shared current-tab search.

Each **Truck** cell has a right-aligned **⇄** button (**F4** or **Alt+Down** when focused) that opens the replacement comparison popup. Its candidates use the same enabled base-game/owned-DLC catalog as Tier list, regardless of Tier list groups or filters. Class and default-tire filters combine; column headers sort the list. The popup uses the shared double-Shift search with a three-character minimum to search all displayed strings and attached metadata. Selecting a candidate updates the resizable lower comparison table: current map equipment versus candidate defaults, internal component names, nonvisual installed addons, vehicle properties, compatible wheel families/tires and nonvisual addon socket options. Truck/Class/Truck ID rows and detailed engine, gearbox, suspension and winch settings are omitted from the comparison. Socket options shared by both trucks are always hidden, independently of the Differences only checkbox. The comparison uses an animated pixel-scrolling viewport instead of jumping by variable-height rows; wheel input over the table, keyboard navigation and shared search all use this viewport. Changed values are highlighted, with a **Differences only** checkbox. Socket matches alone do not validate addon conflicts or other restrictions; explicit definition values do not fully resolve templates. The **Apply replacement** button saves the selected truck as a persistent draft only. Closing the popup refreshes the table preview, with the preview truck highlighted and its file-backed original retained. No map or backup files are written by the popup. Use **Stage changes** in Map trucks or Truck randomization, then **Start → Map files → Apply pending map changes** to commit staged replacements with default equipment. Placement IDs, transforms and bytes outside the changed model/equipment fields are preserved.

The catalog matches placement IDs to nested task/contract settings in the active workspace. Explicit `REWARD` actions indicate obtainable task vehicles; `DESTROY` and `mustDestroyAfterSubstage` indicate mission-only vehicles. Untagged world placements are labeled **Obtainable — discovery/start**, an inference that includes starting vehicles. Named placements without an explicit ownership rule, and conflicting reward/removal rules, remain **Unverified**. Classification evidence, map coordinates and source metadata remain available internally for search. This is a catalog of the selected map files, not the player's save progress. Use a workspace from the same game version as the maps. Reading does not modify or extract the source archives.

Regions-Trucks waits for the shared workspace/ownership snapshot without waiting for unrelated editor warm-up. Map scanning matches known ASCII truck signatures before decoding placement records. Equipment definitions, parent chains, wheel families, addon sockets, default summaries and comparison properties are cached per catalog. Replacement popups reuse the region catalog, read the live enabled-truck selection each time, and calculate full comparisons only for the original and selected candidates; late background results cannot replace a newer selection. Reloading the workspace or invalidating a file changes the content version so stale catalogs are not reused. Reload maps after external workspace edits. See [loading-performance.md](../../loading-performance.md) for local benchmark results.

Packing keeps `[strings]` as top-level PAK content; only `[ps]` and `[ps_common]` are written into `initial.cache_block`. Regular assets use ZIP deflate compression (while `pak.load_list` and `.pct_header` files are stored) to avoid producing archives several times larger than the original.

Small improvements: Engines uses a short one-line description; Custom tires include their underlying category. The shared search uses Tab/Shift+Tab to cycle focus through matches, wrapping at either end. Farming Tractor is an app-only class for Ankatra 1160, Futom 7290RA, Kirovets K-700 and K-7M; XML TruckType values are preserved. The Start tab has a bottom activity bar that animates while unpacking/merging or packing, and resets on completion, cancellation or error. Replacement comparisons hide hood-ornament and miscellaneous addon categories and the requested technical fields, with only Compatible families and scale under Wheels.

Replacement outputs are stored separately under the workspace root: `region-maps/updated/level_*.pak` (or `level_*/[scene]/data_for_ssl.bin` for extracted maps). The first original is kept under `region-maps/backups/<map>/original.pak` or `original.bin`; further saves also preserve a timestamped copy of the preceding edited version. Input archives, original extracted maps and player saves are not overwritten. These map outputs are separate from the initial.pak build in the Start PAK section and are not installed into the game automatically. The catalog prefers saved maps belonging to the selected map folder and workspace. Save checks the scanned metadata hash, exact placement boundary and transform, verifies the patch by re-reading placements, verifies backup bytes, stages archive changes in a temporary file, re-reads the written metadata and checks the full source file hash before an atomic output replacement. In-game behavior has not been validated by the automated checks.

The [official truck placement documentation](https://expeditions-guides.saber.games/map_modding/creating_a_map/trucks/adding_trucks/) describes placement IDs as objective references and the vehicle defaults/upgrades used by this replacement behavior.

## Start: PAK and map changes

The first tab is **Start**, with separate **PAK** and **Map files** sections. Both show before/after values and distinguish **In files** (green) from **Pending** (amber). The baseline for default game values is the workspace's preserved `initial.pak/original_files` tree; map changes use the preserved original map backup. The dashboard refreshes when Start is opened, after Start actions, or via **Refresh changes**. Search and column sorting work in both change tables.

The PAK section lists actual changes in edited workspace files, including XML attribute changes, and unsaved changes in the rank XP, engine compatibility/properties and winch compatibility/properties editors. **Apply pending PAK edits** uses the editors' existing validation and save methods; successful edits move from Pending to In files. **Pack to new PAK…** saves pending editor edits before building a new archive and refuses to overwrite the selected input PAK. Files already saved from other editor tabs appear as In files.

Truck choices from the replacement popup are persisted in `region-maps/pending-replacements.json`, independently of edited maps. Map trucks previews these choices with a Draft or Staged state and retains the original file identity for later application. Changes can be revised in the popup, which returns the affected placement to Draft; staged changes can be discarded on Start. **Apply pending map changes** is the only UI action that writes replacement map files. It validates the source metadata, processes same-map edits in descending binary-offset order, saves each map once with original/previous backups, and clears only the successfully committed plans. Stale plans remain pending for review. Outputs remain separate map copies; no source archives, preserved originals or player saves are overwritten.
## Workspace layout

Choose the workspace root in Start. Initial.pak data and map data are separated:

```text
workspace/
  initial.pak/
    original_files/
    updated/
  region-maps/
    pending-replacements.json
    updated/
    backups/
  progression-settings.json
```

The `initial.pak` entry above is a folder, not the source game archive. The app resolves original/edited initial.pak files there, while map outputs, map backups, pending replacements and progression settings live directly under the workspace root. Metadata is excluded from packed game archives.

Older saved selections such as `workspace/updated` or `workspace/initial.pak/updated` are normalized to the workspace root. On opening or browsing to an older workspace, the app moves the old `.snowpaktool` contents to the root and groups the old `original_files` and `updated` folders under `initial.pak`. Existing conflicting destination data is retained under `layout-backups` before the active legacy data is moved. Stored metadata paths are remapped if necessary, retaining a copy of the prior JSON. Repeating the migration leaves the completed layout unchanged.
## Explicit map staging

Manual replacements, randomization, and original resets are saved as drafts first. Both Randomizer → Truck randomization and Game data → Map trucks have a Stage changes button for the same shared plan. Stage includes all current drafts, including hidden regions; Start lists/counts and applies only staged placements. Editing a staged placement returns that placement to Draft. Drafts and staged plans survive restarts. Applying staged edits keeps unrelated drafts on the same map and updates their source offsets/hash. Earlier saved plans without a staging flag remain staged for compatibility.

Map trucks also has Reset all to original, covering every loaded placement regardless of selected regions or table filters. It restores the original model and exact equipment in the draft and clears randomization assignments. Stage the restoration, then Apply from Start to write map outputs. The Change state column distinguishes Draft, Staged, and In files. Source archives and preserved originals remain unchanged.
